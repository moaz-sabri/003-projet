# وثيقة المواصفات النهائية — القالب التجاري الخفيف

الإصدار 1.0 · مرحلة تحديد المتطلبات · دون كود تنفيذ

## 1. تعريف المشروع

إنشاء قالب ويب تجاري خفيف ومستقل، قابل للتثبيت كتطبيق PWA، يوفّر واجهة عامة لعرض المنتجات وتصنيفاتها، وسلة لإنشاء الطلبات، ولوحة إدارة خاصة بمدير واحد.

يُخصّص القالب من الكود عند إنشاء كل نسخة، عبر كلاس إعدادات مركزي يحدد نوع النشاط، وتسميات المواقع، والحقول الإضافية، وأنواع الطلبات، وشروطها.

يبدأ التنفيذ بنموذج مطعم أو مقهى، مع تصميم تقني يسمح بإعادة استخدام القالب لاحقًا لمعرض سيارات مستعملة أو متجر أو مول أو نشاط مشابه، دون بناء نظام متعدد الشركات أو منشئ قوالب معقد.

الهدف الأساسي: أقل تكلفة وأقل تعقيد ممكنين، مع أمان مناسب، وتجربة استخدام بسيطة، وقابلية واضحة للصيانة والتطوير.

## 2. المبادئ الملزمة

1. نسخة مستقلة لكل نشاط تجاري، وليست منصة متعددة المستأجرين.
2. مدير واحد فقط، دون نظام تسجيل حسابات أو أدوار متعددة.
3. قاعدة SQLite واحدة على السيرفر، دون قاعدة بيانات منفصلة للواجهة أو الإدارة.
4. التخصيص الهيكلي من الكود فقط، عبر كلاس إعدادات واضح.
5. اللغة العربية واتجاه RTL مدعومان من البداية.
6. لا يُسمح بإرسال الطلبات أو استخدام لوحة الإدارة دون اتصال بالسيرفر.
7. يمكن تصفح المنتجات المحفوظة مسبقًا دون اتصال بالإنترنت.
8. كل طلب مستقل، حتى عند ارتباط عدة طلبات بالموقع نفسه.
9. لا دفع إلكتروني، ولا محاسبة أو مخزون متقدم في الإصدار الأول.
10. لا يُؤكَّد نجاح أي طلب قبل حفظه بنجاح على السيرفر.

## 3. البنية التقنية

| المكوّن        | القرار                                        |
| -------------- | --------------------------------------------- |
| لغة الخادم     | PHP                                           |
| قاعدة البيانات | SQLite                                        |
| الواجهة        | HTML وCSS وJavaScript                         |
| واجهة الاتصال  | PHP API بسيطة ومنظمة                          |
| تطبيق الهاتف   | PWA مع Service Worker                         |
| بيئة التطوير   | Docker                                        |
| النشر          | رفع مباشر إلى استضافة PHP عادية               |
| الصور          | رفع محلي إلى السيرفر، مع تصغيرها وضبط أنواعها |
| المصادقة       | مدير واحد بإعدادات دخول خاصة على السيرفر      |
| اللغة الأساسية | العربية وRTL                                  |

يجب ألا يتطلب تشغيل النسخة المنشورة وجود Docker على الاستضافة. وتُحفظ قاعدة البيانات وإعدادات الدخول والملفات الحساسة خارج المسارات العامة التي يمكن الوصول إليها عبر المتصفح.

## 4. كلاس إعدادات المشروع

يُنشأ كلاس مركزي باسم `ProjectConfig`، أو اسم مكافئ، يكون المرجع الوحيد لإعدادات النسخة الهيكلية.

أ. الهوية والعرض

اسم النشاط، الشعار، الأيقونة، رسالة الترحيب، اللغة، اتجاه الواجهة، العملة والمنطقة الزمنية.

ب. نوع النشاط والمواقع

نوع النشاط، تسمية الموقع المفرد والجمع، اشتراط تحديد الموقع، وطريقة تفسير QR.

ج. حقول المنتجات

الحقول الأساسية، والحقول الإضافية، وأنواع المدخلات، والقيم الافتراضية، وقواعد التحقق، وترتيب العرض.

د. قواعد الطلبات

أنواع الطلبات المتاحة، حقول كل نوع، قواعد التحقق، حالات الطلب، وسياسة تحديد الموقع.

هـ. الوظائف المفعّلة

الميزات اللازمة لهذه النسخة فقط، دون تحميل المشروع أنظمة لا يحتاج إليها.

تكون إعدادات الهيكل من الكود، بينما تُحفظ البيانات التشغيلية التي تحتاج إلى إدارة يومية، مثل المنتجات والتصنيفات والطلبات، في SQLite. ويمكن تعديل اسم النشاط وشعاره من لوحة الإدارة إذا كانت هذه الخاصية مفعّلة في الإعدادات.

قاعدة التنفيذ: لا يُنشأ نظام مرن يسمح بتعديل تعريفات الحقول أو قواعد التحقق من لوحة الإدارة. تعديل الهيكل يتطلب تعديل الكود وإصدار نسخة جديدة.

## 5. واجهة الزبون

### 5.1 صفحة الترحيب

- عرض اسم النشاط والشعار.
- عرض رسالة ترحيبية اختيارية.
- زر واضح للانتقال إلى المنتجات.
- تصميم متجاوب مع الهواتف والحواسيب.
- دعم العربية واتجاه RTL.
- إظهار حالة الاتصال عند الحاجة، دون إزعاج المستخدم برسائل متكررة.

### 5.2 صفحة المنتجات

تعرض الصفحة قائمة المنتجات وفق التصنيفات وترتيبها المحدد في الإدارة.

البيانات الأساسية لكل منتج:

- الاسم.
- الصورة.
- وصف مختصر اختياري.
- التصنيف.
- السعر.
- حالة التوفر.

تدعم الصفحة التنقل بين التصنيفات، وإظهار المنتجات المتاحة، والبحث البسيط إذا كان مفعّلًا في الإعدادات.

### 5.3 صفحة تفاصيل المنتج

لا تُفتح صفحة فرعية إلا عندما يكون للمنتج تفاصيل إضافية تستحق العرض.

يمكن أن تحتوي على صورة أكبر، ووصف كامل، وخصائص المنتج الإضافية، والسعر وزر الإضافة إلى السلة.

أما المنتج الذي لا يملك تفاصيل إضافية، فيمكن إضافته إلى السلة مباشرة من القائمة.

### 5.4 السلة وإتمام الطلب

تدعم السلة:

- إضافة المنتجات وتعديل الكميات وحذف العناصر.
- عرض السعر والإجمالي بوضوح.
- مراجعة الطلب قبل إرساله.
- طلب اسم الزبون عند إتمام الطلب فقط.
- عرض الموقع المحدد مسبقًا إذا وصل الزبون من QR.
- إظهار حقول إضافية عند الحاجة وفق إعدادات نوع الطلب.

لا يُطلب إنشاء حساب، ولا يُطلب البريد الإلكتروني أو الهاتف في النموذج الأساسي. ويمكن أن تضيف نسخة مستقبلية حقولًا أخرى عند وجود حاجة فعلية.

QR الطلب

يرتبط بطلب محدد، ويُستخدم لفتح معلومات ذلك الطلب ضمن الحدود التي تسمح بها صلاحية الرابط. لا يمنح تلقائيًا صلاحية تعديل الطلب أو إلغائه.

### القواعد الملزمة

1. مسح QR الموقع لا ينشئ طلبًا على السيرفر مباشرة؛ بل يحدد الموقع في جلسة التصفح.
2. إنشاء الطلب يحدث عند إرسال السلة بنجاح.
3. كل عملية إرسال ناجحة تنشئ طلبًا مستقلًا بمعرّف فريد.
4. إذا أنشأ زبونان طلبين على الطاولة نفسها، يظهر الطلبان منفصلين.
5. لا يُدمج طلب جديد مع طلب سابق، حتى لو كان الموقع نفسه.
6. يُحدد كلاس الإعدادات ما إذا كان الموقع إلزاميًا أو اختياريًا.
7. عند اشتراط الموقع، يمنع السيرفر إنشاء الطلب دون موقع صالح، وليس الواجهة فقط.
8. إذا كان الموقع معطّلًا أو غير موجود، يرفض السيرفر الطلب عند اشتراطه.
9. رمز الطلب يستخدم قيمة عشوائية يصعب تخمينها، مع عدم كشف بيانات داخلية حساسة.

يمكن إنشاء QR للمواقع والطلبات وطباعتها من لوحة الإدارة، دون الاعتماد على خدمة خارجية مدفوعة لتوليد الرموز.

## 7. دورة حياة الطلب

الحالات الافتراضية في النسخة الأولى:

`جديد ← قيد التنفيذ ← مكتمل`

مع حالة مستقلة للإلغاء.

يمكن أن تضيف الإعدادات حالات أكثر عند الحاجة، لكن لا حاجة إلى نظام سير عمل معقد.

عند الإرسال، ينفّذ السيرفر الخطوات التالية:

1. التحقق من صحة الطلب والمدخلات.
2. التحقق من المنتجات وأسعارها الحالية وحالة توفرها.
3. التحقق من الموقع وفق إعدادات النسخة.
4. حساب الإجمالي على السيرفر.
5. حفظ الطلب وعناصره ضمن معاملة قاعدة بيانات واحدة.
6. حفظ اسم المنتج وسعره وكميته وقت إنشاء الطلب.
7. إرجاع رقم الطلب وتأكيد الحفظ للزبون.

إذا فشل الحفظ، لا يظهر الطلب على أنه ناجح. ويجب أن تتضمن آلية الإرسال حماية من تكرار إنشاء الطلب بسبب إعادة المحاولة بعد انقطاع الاتصال أو تأخر الاستجابة، باستخدام مفتاح idempotency مناسب.

إلغاء الطلب من الإدارة يغيّر حالته، ولا يحذف السجل نهائيًا في التشغيل الطبيعي. ولا يجوز أن يؤدي إلغاء طلب إلى تغيير حالة طلب آخر مرتبط بالموقع نفسه.

## 8. لوحة الإدارة

تكون لوحة الإدارة صغيرة وواضحة، وتحتوي على:

| القسم         | الوظائف                                                    |
| ------------- | ---------------------------------------------------------- |
| الرئيسية      | ملخص الطلبات الجديدة والوصول السريع إلى الأقسام            |
| التصنيفات     | إضافة وتعديل وحذف وترتيب التصنيفات                         |
| المنتجات      | إضافة وتعديل وحذف، الصور، الأسعار، الحقول الإضافية والتوفر |
| الطلبات       | عرض القائمة والتفاصيل، تغيير الحالة، والإلغاء              |
| المواقع وQR   | إنشاء المواقع وتعديل أسمائها وحالاتها وتوليد رموزها        |
| إعدادات العرض | تعديل الاسم والشعار ورسالة الترحيب والخيارات المسموحة      |

لا تتضمن لوحة الإدارة إعداد نوع النشاط، أو تعريف حقول جديدة، أو إنشاء مستخدمين إضافيين. هذه أمور تخص كلاس إعدادات الكود.

يجب أن تظهر الطلبات الجديدة بوضوح. يكفي في النسخة الأولى تحديث دوري بسيط للقائمة بدل بناء WebSocket أو بنية إشعارات لحظية.

## 9. نموذج البيانات

تعتمد النسخة الأولى على قاعدة SQLite واحدة.

| الجدول           | البيانات الأساسية                                                            |
| ---------------- | ---------------------------------------------------------------------------- |
| `settings`       | إعدادات العرض التشغيلية المسموح تعديلها                                      |
| `categories`     | الاسم، الترتيب، وحالة التفعيل                                                |
| `products`       | الاسم، السعر، الصورة، الوصف، التصنيف، التوفر                                 |
| `locations`      | معرّف الموقع، الاسم، النوع، الحالة                                           |
| `orders`         | معرّف فريد، الرقم الظاهر، الاسم، الموقع الاختياري، الحالة، الإجمالي والتوقيت |
| `order_items`    | الطلب، المنتج المرجعي، اسم المنتج وسعره المحفوظان، الكمية والإجمالي          |
| `admin_sessions` | الجلسات النشطة إذا تقرر تخزينها في SQLite                                    |

أما الحقول الإضافية للمنتجات، فتُعرّف في `ProjectConfig`، وتُخزّن قيمها في بنية مناسبة مثل JSON عندما تكون بسيطة. لا حاجة إلى إنشاء نظام جداول ديناميكي كامل.

يمكن إضافة جدول لسجل تغييرات الطلبات إذا اقتضت متطلبات التتبع ذلك، لكنه ليس شرطًا لتشغيل النموذج الأول.

تُستخدم المفاتيح الخارجية والقيود المناسبة، والمعاملات عند حفظ الطلب، وتُحفظ النسخ الاحتياطية بطريقة آمنة. ولا يجوز أن تكون قاعدة البيانات أو مجلد النسخ الاحتياطية متاحين عبر URL عام.

## 10. الأمان

رغم أن النظام مخصص لمدير واحد، يجب حماية نقاط الدخول والبيانات منذ البداية.

### المصادقة

- بيانات الدخول تُعرّف في إعدادات خاصة بالسيرفر، وليست في ملفات JavaScript أو HTML العامة.
- كلمة المرور تُخزّن على شكل تجزئة آمنة باستخدام آليات PHP المناسبة.
- جلسة الإدارة تستخدم ملفات تعريف ارتباط آمنة، مع إعدادات `HttpOnly` و`Secure` عبر HTTPS و`SameSite`.
- تجديد معرّف الجلسة بعد تسجيل الدخول، وإنهاء الجلسة عند الخروج.
- تحديد محاولات تسجيل الدخول، وعدم كشف معلومات حساسة عند فشل المصادقة.

### حماية البيانات والطلبات

- حماية عمليات التعديل والإلغاء من CSRF.
- التحقق من المدخلات على السيرفر.
- استخدام استعلامات SQL المحضرة.
- منع الوصول غير المصرح به إلى لوحة الإدارة وواجهات API الخاصة بها.
- التحقق من صلاحيات الوصول إلى كل طلب أو رابط خاص به.
- منع تعديل الأسعار والإجماليات من جانب الزبون.
- التحقق من ملفات الصور وأحجامها وأنواعها، وتوليد أسماء آمنة.
- حماية ملفات الإعدادات وقاعدة البيانات والنسخ الاحتياطية.
- عدم تضمين أسرار أو كلمات مرور في المستودع البرمجي.

يجب أن تتوفر حماية مناسبة من الطلبات المكررة، ومن الوصول المباشر إلى الملفات الحساسة، ومن إساءة استخدام واجهات الطلبات.

## 11. PWA والعمل دون اتصال

الهدف هو أن يشعر المستخدم بأنه يستخدم تطبيقًا خفيفًا، دون بناء تطبيق أصلي مستقل.

### الوظائف المطلوبة

- ملف `manifest` صحيح، مع اسم التطبيق وأيقوناته.
- Service Worker لتخزين ملفات الواجهة الأساسية.
- تثبيت التطبيق على الأجهزة المتوافقة.
- تصميم متجاوب مع أحجام الشاشات المختلفة.
- تخزين مؤقت للمنتجات والتصنيفات والصور التي جرى تحميلها بنجاح.
- إظهار البيانات المخزنة عند انقطاع الاتصال.
- توضيح أن البيانات غير المتصلة قد تكون قديمة.
- منع إرسال الطلبات وإدارة المنتجات والطلبات دون اتصال.

### قواعد مهمة

- لا يوجد طابور طلبات ينتظر المزامنة عند عودة الاتصال.
- لا تُعرض رسالة نجاح طلب عند تعذر الوصول إلى السيرفر.
- عند عودة الاتصال، يمكن تحديث بيانات المنتجات المخزنة.
- يجب أن تتعامل الواجهة مع فشل الشبكة حتى لو أظهر الجهاز أنه متصل بالإنترنت.
- يجب ألا تخزّن استجابات لوحة الإدارة الحساسة في Cache عام.

بهذا نحقق التصفح دون إنترنت دون تعقيد مزامنة البيانات أو معالجة تعارضات الطلبات.

## 12. بنية الملفات والنشر

البنية المقترحة:

```
project/
├── index.php            نقطة دخول واجهة الزبون على الجذر (روابط نظيفة)
├── app/
│   ├── index.html       قالب الواجهة (يُقدَّم عبر index.php)
│   ├── assets/
│   ├── css/
│   └── js/
├── admin/
├── api/
│   ├── index.php
│   ├── routes/
│   ├── services/
│   └── repositories/
├── src/
│   └── Config/
│       └── ProjectConfig.php
├── storage/
│   ├── database/
│   ├── uploads/
│   └── backups/
├── tests/
├── Dockerfile
├── compose.yaml
└── README.md
```

هذه بنية تنظيمية مقترحة وليست شرطًا لتوزيع الملفات حرفيًا. الأولوية أن تكون المسؤوليات واضحة دون الإفراط في تقسيم المشروع إلى طبقات وملفات لا تضيف قيمة.

### متطلبات النشر

1. تشغيل المشروع محليًا باستخدام Docker.
2. إمكانية رفع ملفات النسخة الجاهزة إلى استضافة PHP عادية.
3. عدم الحاجة إلى Docker في بيئة الإنتاج التقليدية.
4. ضبط صلاحيات الكتابة على قاعدة البيانات ومجلد الصور فقط حسب الحاجة.
5. حماية المسارات الحساسة من الوصول المباشر.
6. توفير خطوات واضحة لتهيئة قاعدة البيانات وإعداد بيانات دخول المدير.
7. توثيق النسخ الاحتياطي والاستعادة والتحديثات.
8. توفير إعدادات منفصلة لبيئة التطوير والإنتاج دون تضمين الأسرار في الملفات العامة.

## 13. الاختبارات ومعايير القبول

لا يُعتبر المشروع جاهزًا لمجرد أن الواجهات تظهر بشكل صحيح. يجب اجتياز الاختبارات التالية قبل نشر النسخة الأولى.

واجهة الزبون

- عرض التصنيفات والمنتجات بصورة صحيحة.
- فتح تفاصيل المنتج فقط عند وجود تفاصيل تستحق العرض.
- عمل السلة وحساب الكميات والإجمالي.
- طلب اسم الزبون عند الإتمام فقط.
- العمل بشكل مقبول على الهاتف والحاسوب مع دعم RTL.

الطلبات وQR

- كل إرسال ناجح ينشئ طلبًا مستقلًا.
- يمكن إنشاء عدة طلبات للموقع نفسه دون دمجها.
- يُرفض الطلب دون موقع إذا كان الموقع إلزاميًا في الإعدادات.
- تُحفظ الأسعار وقت إنشاء الطلب.
- لا يؤدي تكرار محاولة الإرسال إلى إنشاء طلبات مكررة.
- لا يُعرض تأكيد الطلب إلا بعد نجاح الحفظ.

الإدارة والأمان

- منع الوصول إلى لوحة الإدارة دون مصادقة.
- منع تعديل الطلبات أو المنتجات دون صلاحية.
- رفض الملفات غير المسموح بها عند رفع الصور.
- التحقق من المدخلات والأسعار على السيرفر.
- منع الوصول المباشر إلى قاعدة البيانات والإعدادات والنسخ الاحتياطية.

PWA والنشر

- إمكانية تثبيت التطبيق على الأجهزة المتوافقة.
- تصفح البيانات المخزنة دون اتصال.
- تعطيل إرسال الطلبات وإدارة النظام عند انقطاع الاتصال.
- نجاح التشغيل في Docker وفي استضافة PHP عادية.
- إمكانية إنشاء نسخة احتياطية واستعادتها.

## 14. خارج نطاق الإصدار الأول

لن تشمل النسخة الأولى:

- تعدد الشركات أو المستأجرين.
- حسابات الزبائن أو الموظفين.
- نظام صلاحيات متعدد الأدوار.
- الدفع الإلكتروني.
- نظام محاسبة وفواتير ضريبية متكامل.
- إدارة مخزون متقدمة.
- مزامنة الطلبات دون اتصال.
- الإشعارات اللحظية عبر بنية خارجية.
- تطبيقات Android وiOS أصلية.
- منشئ قوالب ديناميكي أو تعديل الحقول من لوحة الإدارة.
- تعدد السيرفرات أو قواعد البيانات.
- تكاملات خارجية لا تحتاجها الوظائف الأساسية.

يمكن دراسة هذه الوظائف لاحقًا، لكن لا تدخل ضمن التزامات الإصدار الأول.

## 15. مراحل التنفيذ المقترحة

يُنفَّذ المشروع على مراحل مستقلة، مع التحقق من كل مرحلة قبل الانتقال إلى التالية.

| المرحلة                | النتيجة المطلوبة                                          |
| ---------------------- | --------------------------------------------------------- |
| 1. الأساس التقني       | بنية الملفات، Docker، SQLite، الإعدادات، والتهيئة الأولية |
| 2. المنتجات والتصنيفات | إدارة البيانات الأساسية وعرضها عبر API                    |
| 3. واجهة الزبون        | الترحيب، التصنيفات، المنتجات، التفاصيل والسلة             |
| 4. الطلبات وQR         | إنشاء الطلبات المستقلة، ربط المواقع، ومنع التكرار         |
| 5. لوحة الإدارة        | المصادقة وإدارة المنتجات والطلبات والمواقع                |
| 6. PWA                 | التثبيت والتخزين المؤقت والتصفح دون اتصال                 |
| 7. الأمان والاختبارات  | مراجعة الصلاحيات والمدخلات والملفات والطلبات              |
| 8. النشر والتوثيق      | اختبار استضافة PHP عادية، ونسخ احتياطي، وتوثيق عربي       |

لا ينبغي الانتقال إلى المرحلة التالية إذا كانت المرحلة الحالية تحتوي على أخطاء أساسية. كما يجب أن يتضمن كل إصدار تغيّرًا واضحًا في الوظائف واختبارات تثبت صحته.

## 16. تعريف النجاح

يُعتبر الإصدار الأول ناجحًا عندما يستطيع مدير واحد تثبيت نسخة مستقلة، وإضافة منتجات وتصنيفات، ورفع الصور، وإنشاء رموز QR للمواقع، واستقبال الطلبات وإدارتها، بينما يستطيع الزبون تصفح المنتجات من هاتفه وإرسال طلب باسم بسيط عند توفر الاتصال.

ويجب أن يتحقق ذلك دون اشتراكات لخدمات خارجية ضرورية لتشغيل الوظائف الأساسية، ودون قاعدة بيانات منفصلة لكل قسم، ودون تعقيد تقني لا يخدم الاستخدام الفعلي.

القرار النهائي: هذه الوثيقة هي نطاق الإصدار الأول المعتمد. لا حاجة الآن إلى إضافة ميزات جديدة أو توسيع الفكرة. الخطوة التالية هي تحويل المواصفات إلى خطة تنفيذ تقنية مفصلة، ثم البدء بالمرحلة الأولى، دون كتابة المشروع كاملًا دفعة واحدة.
